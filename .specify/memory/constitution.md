# Podlodka SSD Frontend Constitution

## Core Principles

### I. Каждая FEOD-сущность имеет явную роль

Каждый файл и каталог MUST иметь понятную роль в структуре проекта. Роль определяет ожидаемое
содержимое, допустимые ограничения и отношения с соседними сущностями.

Нейтральные контейнеры без устойчивого смысла (`stuff`, `misc` и подобные) запрещены.
FEOD-сущность нельзя определять через DDD entity: структурная сущность FEOD и доменная сущность
DDD — разные понятия. Если роль нельзя кратко и однозначно назвать, структуру MUST пересмотреть.

### II. Проект использует пять канонических уровней

Верхняя структура проекта MUST состоять только из уровней `app`, `pages`, `modules`, `common` и
`global`. Каждый уровень хранит только свою ответственность:

- `app` — запуск, композиция и wiring приложения;
- `pages` — пользовательские маршруты, экраны и route-level композиция;
- `modules` — самостоятельные продуктовые ответственности и сценарии;
- `common` — переиспользуемые технические и UI-сущности без продуктовой привязки;
- `global` — глобальные эффекты и инфраструктурные подключения.

Новые верхние уровни и альтернативные имена (`globals` и подобные) запрещены без отдельного
архитектурного решения. Частота использования не превращает продуктовый код в `common`, а
импортируемый общий код — в `global`.

### III. Модуль выражает одну самостоятельную ответственность

Модуль MUST создаваться вокруг одной продуктовой области, которую нужно развивать, тестировать и
использовать как единое целое. Его внутренности MAY включать `ui`, `model`, `api`, `lib`, типы и
тесты, только если они служат этой ответственности.

Объединять в одном модуле несвязанные helpers, UI, API и состояние ради удобства навигации
запрещено. Основная бизнес-логика MUST NOT находиться в `app`, `pages` или `common`. Сценарий,
выходящий за границы одного маршрута, MUST быть оформлен в `modules`.

### IV. Внешнее использование проходит через минимальный public API

Каждый модуль MUST иметь корневой `index.ts` как единственный поддерживаемый public API. Внешний
код MUST использовать только экспортированные из него компоненты, функции, hooks, providers и
типы. Остальное является приватной реализацией.

Public API MUST проектироваться намеренно и оставаться минимальным. Механический `export *`,
экспорт transport-деталей, debug-кода или внутреннего состояния без подтверждённой потребности
потребителя запрещён. Собственный `index.ts` подмодуля не делает его внешним контрактом: доступ
наружу MUST явно открыть родительский модуль.

### V. Импорты следуют разрешённой матрице зависимостей

Направление зависимости MUST совпадать с направлением импорта: если `A` импортирует `B`, то `A`
зависит от `B`. Разрешена следующая матрица:

| Уровень-источник | Разрешённые импорты |
| --- | --- |
| `app` | `pages`, `modules`, `common` |
| `pages` | `modules`, `common` |
| `modules` | `common` и public API других модулей |
| `common` | public API других сущностей `common` и внешние пакеты |
| `global` | ничего из уровней FEOD |

`app` MUST NOT импортироваться другими уровнями. `pages` MUST NOT импортироваться из `pages`,
`modules`, `common` или `global`. Прикладной код MUST NOT импортировать `global` как обычную
зависимость. `global` MUST подключаться только через entrypoint, bootstrap, конфигурацию сборки,
HTML-шаблон или тестовую инфраструктуру.

Эти правила одинаково применяются к runtime- и type-only imports. Deep imports во внутренние
файлы чужой FEOD-сущности запрещены.

### VI. Предметная логика остаётся рядом с владельцем

Повторное использование не отменяет принадлежность к ответственности. Доменная модель, сценарное
состояние, API и бизнес-правила MUST оставаться внутри соответствующего модуля или его подмодуля.
В `common` допускаются только нейтральные технические сущности, не знающие о конкретном продукте
или предметной области.

`global` содержит только декларации, shims, polyfills, расширения глобальных типов и
контролируемые side effects. UI, helpers, stores, API-клиенты и продуктовые константы MUST NOT
попадать в `global` под видом кода, который нужен «везде».

### VII. Структура растёт фрактально и по реальной ответственности

Большой модуль MAY развиваться по тем же принципам, что и проект: устойчивую внутреннюю область
MAY оформить как подмодуль с локальной структурой и контрактом. Подмодули MUST оставаться частью
родительского модуля, пока родитель явно не экспортирует их наружу.

Преждевременное дробление и механическое углубление структуры запрещены. Глубина более трёх
уровней требует документированного архитектурного обоснования, которое показывает реальные
границы ответственности и сохранение читаемости.

### VIII. Архитектура проверяется по контрактам и риску изменений

Каждое архитектурное изменение MUST быть проверяемым в ревью и автоматизированных проверках.
Проверяются как минимум роль сущности, граница ответственности, соблюдение матрицы импортов,
отсутствие deep imports и минимальность public API.

Тесты MUST располагаться рядом с ответственностью, которую они проверяют: unit-тесты — для
локальной логики, component-тесты — для UI-контрактов, integration-тесты — для связанного сценария.
Страница или end-to-end-тест MUST NOT быть единственной проверкой поведения модуля. README модуля
MUST добавляться, когда назначение, public API или границы нельзя однозначно понять из кода.

## Технологические требования и контроль качества

- Тесты являются главным критерием готовности изменений. Каждая функция MUST быть покрыта
  unit-тестами.
- Для каждого модуля MUST существовать интеграционный тест с именем
  `<module-name>.integration.test.tsx`.
- Скриншотные тесты MUST NOT добавляться. UI MUST проверяться через запросы React Testing Library,
  включая семейства `getBy*`, `findBy*` и `queryBy*`.
- Работа с API MUST выполняться через `@tanstack/query`: получение данных — через `useQuery`, любые
  изменения данных — через `useMutation`.
- UI MUST строиться на компонентах Ant Design (`antd`). Кастомные стили допускаются только после
  явной проверки, что компоненты и настройки темы Ant Design не решают задачу; такие стили MUST
  размещаться в `*.module.css`.
- Lefthook и все настроенные pre-commit проверки MUST выполняться перед фиксацией изменений.
  Игнорировать их ошибки или обходить pre-commit этап запрещено.

## Архитектурное ревью и исключения

Перед принятием изменения автор и ревьюер MUST подтвердить:

1. Роль каждого нового файла, каталога и уровня понятна.
2. Одна сущность не смешивает независимые ответственности.
3. Матрица зависимостей соблюдена.
4. Внешние импорты проходят через public API без deep imports.
5. Предметная логика не попала в `common` или `global`.
6. Не создана лишняя вложенность или преждевременный подмодуль.
7. Тесты, документация и автоматические проверки соответствуют риску изменения.

Нарушение принципа MUST быть исправлено до слияния либо оформлено как исключение. Исключение
допускается только когда оно:

1. необходимо для конкретного миграционного, инфраструктурного или framework-сценария;
2. ограничено по области и сроку действия;
3. описано в архитектурном решении с причиной, затронутыми сущностями и планом возврата к норме;
4. контролируется автоматической проверкой или отдельным обязательным пунктом ревью.

Допустимые классы исключений включают подключение `global` через инфраструктурную точку входа,
test setup или build-time конфигурацию; временный migration alias, ведущий к public API; отсутствие
README у маленького модуля с очевидными границами. Каждый случай всё равно MUST пройти описанную
процедуру и не является исключением по умолчанию.

## Governance

Эта конституция имеет приоритет над локальными соглашениями, привычками команды и документацией,
которая ей противоречит. Каждый план, задача и code review MUST проверять соответствие её
принципам; необоснованная сложность MUST быть устранена либо оформлена как ограниченное исключение.

Поправка MUST быть предложена отдельным документированным изменением, описывать мотивацию, влияние
на существующий код и план миграции. Она вступает в силу после явного одобрения ответственных за
архитектуру проекта и обновления этой конституции.

Версия конституции следует semantic versioning: MAJOR — несовместимое удаление или переопределение
принципа; MINOR — новый принцип, раздел или существенное расширение требований; PATCH — уточнение
формулировок без изменения обязательств. Дата последней поправки MUST обновляться при каждом
содержательном изменении.

Соответствие MUST проверяться в каждом pull request. Исключения MUST повторно оцениваться до
истечения указанного срока и удаляться после завершения миграции. Периодическое архитектурное
ревью MUST выявлять нарушения матрицы зависимостей, deep imports, чрезмерные public API и
неактуальные исключения.
