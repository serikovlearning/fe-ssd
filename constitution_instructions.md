# Project Structure and Architecture
## Основные принципы

### I. Каждая FEOD-сущность имеет явную роль

Каждый файл и каталог должен иметь понятную роль в структуре проекта. Роль определяет ожидаемое содержимое, допустимые ограничения и отношения с соседними сущностями.

Нельзя создавать нейтральные контейнеры без устойчивого смысла (`stuff`, `misc` и подобные) или объяснять FEOD-сущность через DDD entity: структурная сущность FEOD и доменная сущность DDD — разные понятия. Если роль нельзя кратко и однозначно назвать, структуру необходимо пересмотреть.

### II. Проект использует пять канонических уровней

Верхняя структура проекта состоит только из уровней `app`, `pages`, `modules`, `common` и `global`. Каждый уровень хранит только свою ответственность:

- `app` — запуск, композиция и wiring приложения;
- `pages` — пользовательские маршруты, экраны и route-level композиция;
- `modules` — самостоятельные продуктовые ответственности и сценарии;
- `common` — переиспользуемые технические и UI-сущности без продуктовой привязки;
- `global` — глобальные эффекты и инфраструктурные подключения.

Новые верхние уровни и альтернативные имена (`globals` и т. п.) не вводятся без отдельного архитектурного решения. Частота использования не превращает продуктовый код в `common`, а импортируемый общий код — в `global`.

### III. Модуль выражает одну самостоятельную ответственность

Модуль создаётся вокруг одной продуктовой области, которую нужно развивать, тестировать и использовать как единое целое. Его внутренности могут включать `ui`, `model`, `api`, `lib`, типы и тесты, но только если они служат этой ответственности.

Нельзя объединять в одном модуле несвязанные helpers, UI, API и состояние ради удобства навигации. Основная бизнес-логика не должна жить в `app`, `pages` или `common`; если сценарий выходит за границы одного маршрута, его следует оформить в `modules`.

### IV. Внешнее использование проходит через минимальный public API

Каждый модуль имеет корневой `index.ts`, который является его поддерживаемым public API. Внешний код использует только экспортированные из этого входа компоненты, функции, hooks, providers и типы. Всё остальное является приватной реализацией.

Public API проектируется намеренно и минимально. Нельзя экспортировать внутренности механически через `export *`, открывать transport-детали, debug-код или внутреннее состояние без доказанной потребности потребителя. Наличие собственного `index.ts` у подмодуля само по себе не делает его внешним контрактом: наружу его открывает только родительский модуль.

### V. Импорты следуют разрешённой матрице зависимостей

Направление зависимости совпадает с направлением импорта: если `A` импортирует `B`, то `A` зависит от `B`. Допустимая матрица:

| Уровень-источник | Разрешённые импорты |
| --- | --- |
| `app` | `pages`, `modules`, `common` |
| `pages` | `modules`, `common` |
| `modules` | `common` и public API других модулей |
| `common` | public API других сущностей `common` и внешние пакеты |
| `global` | ничего из уровней FEOD |

`app` не импортируется из других уровней; `pages` не импортируются из `pages`, `modules`, `common` или `global`; прикладной код не импортирует `global` как обычную зависимость. `global` подключается только через entrypoint, bootstrap, конфигурацию сборки, HTML-шаблон или тестовую инфраструктуру.

Правило распространяется одинаково на runtime- и type-only imports. Deep imports во внутренние файлы чужой FEOD-сущности запрещены.

### VI. Предметная логика остаётся рядом с владельцем

Повторное использование не отменяет принадлежность к ответственности. Доменная модель, сценарное состояние, API и бизнес-правила должны оставаться внутри соответствующего модуля или его подмодуля. В `common` допускаются только нейтральные технические сущности, не знающие о конкретном продукте или предметной области.

`global` ещё уже: он содержит только декларации, shims, polyfills, расширения глобальных типов и контролируемые side effects. UI, helpers, stores, API-клиенты и продуктовые константы не должны попадать в `global` под видом кода, который нужен «везде».

### VII. Структура растёт фрактально и по реальной ответственности

Большой модуль можно развивать по тем же принципам, что и проект: устойчивую внутреннюю область оформлять как подмодуль с локальной структурой и контрактом. Подмодули остаются частью родительского модуля, пока родитель явно не экспортирует их наружу.

Структура не дробится преждевременно и не углубляется механически. Глубина более двух-трёх уровней допустима только как редкое, обоснованное исключение, если она выражает реальные границы ответственности и сохраняет читаемость.

### VIII. Архитектура проверяется по контрактам и риску изменений

Каждое архитектурное изменение должно быть проверяемым в ревью и автоматизированных проверках. Проверяются как минимум: роль сущности, граница ответственности, соблюдение матрицы импортов, отсутствие deep imports и минимальность public API.

Тесты располагаются рядом с ответственностью, которую они проверяют: unit-тесты для локальной логики, component-тесты для UI-контрактов и integration-тесты для связанного сценария. Страница или end-to-end-тест не должны быть единственной проверкой поведения модуля. README модуля добавляется, когда назначение, public API или границы неочевидны.

## Архитектурное ревью

Перед принятием изменения автор и ревьюер отвечают на вопросы:

1. Понятна ли роль каждого нового файла, каталога и уровня?
2. Не смешаны ли в одной сущности независимые ответственности?
3. Соблюдена ли матрица зависимостей?
4. Идут ли внешние импорты через public API без deep imports?
5. Не попала ли предметная логика в `common` или `global`?
6. Не создана ли лишняя вложенность или преждевременный подмодуль?
7. Есть ли тесты, документация и автоматическая проверка, соответствующие риску изменения?

Нарушение конституционного принципа требует либо исправления до слияния, либо оформленного исключения по процедуре ниже.

## Исключения и изменения конституции

Исключение допускается только если оно:

1. необходимо для конкретного миграционного, инфраструктурного или framework-сценария;
2. ограничено по области и сроку действия;
3. описано в архитектурном решении с причиной, затронутыми сущностями и планом возврата к норме;
4. проверяется инструментом или отдельным пунктом ревью.

Обычные допустимые классы исключений: подключение `global` через инфраструктурную точку входа, test setup или build-time конфигурацию; временный migration alias, ведущий к public API; README для маленького модуля с очевидными границами.

## Testing
Тесты являются главным критерием готовности изменений.
Все функции должны быть покрыты unit-тестами.
Если мы работаем с модулем то для модуля должен быть создан module-name.integration.test.tsx
Мы не добавляем скриншот тесты.
Для проверки UI используем методы из react testing library: getBy* / findBy* / queryBy* and etc.


## Работа с API
Для работы с API используем `@tanstack/query`.
Для получения данных useQuery, для любых изменений данных - useMutation

## Design library
Мы работаем с библиотекой компонентов antd.
Если необходимо сделать кастомные стили - мы используем style.module.css
Необходимо внимательно провалидировать необходимость использования кастомных стилей.
